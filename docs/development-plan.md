**第 4 阶段：扩展基本句式已完成**。五种基本句型及四种句子用途的限定规则、固定样例、原文成分与嵌套展示已实现。疑问句支持 do/does/did 或 be 开头，祈使句支持原形动词和隐含主语，感叹句限定为带完整主语与 be 的 What/How 结构。范围及验证记录见 [本地分析 0.3.1](local-analysis-scope.md)。

## 第一版目标与范围

第一版为**无 AI、本地运行的英语语法学习工具**。使用随应用提供的词典和人工编写的规则，在浏览器内分析常见简单句，提供彩色成分标注、中文解释、基础纠错和修改后重新分析。

- 不使用大模型或其他机器学习模型，不依赖模型 API、密钥或远程分析服务。
- 安装依赖和构建可能需要联网；完成准备并启动本地服务后，分析过程应能断网运行。本版不承诺双击 HTML 启动或提供离线安装包。
- 每次处理一个英文句子，最多 1000 个 UTF-16 代码单元；空输入、超长输入和多句输入明确提示，不静默截断。
- 以一般现在时、一般过去时、简单名词短语和常见动词为起点，支持主谓、主谓宾、主系表、双宾语、宾补五种基本句型的限定结构。
- 覆盖典型陈述句、使用 do/does/did 或 be 的一般疑问句、简单祈使句，以及固定 What/How 结构的感叹句。句子用途与基本句型分别判断，不只按标点推断。
- 纠错仅覆盖已定义上下文的主谓一致、do/does/did 后动词原形和情态动词后动词原形。复杂时态、任意成分缺失、开放式词序纠正、拼写纠正及自然表达建议暂不承诺。
- 并列句、从句、被动语态、复杂非谓语结构和需要语境消歧的输入不在第一版完整分析范围内。未知词或无法唯一匹配的结构应提示无法可靠分析，不强行套用五种句型。

## 分析方案

采用 **本地词典 + 分词 + 句式规则 + 纠错规则 + 中文解释模板**。

1. 分词保留原文及精确位置，不通过重组单词还原原文。
2. 词典保存候选词性、动词变化及必要的动词搭配信息；词性不直接等同于句子成分。
3. 规则结合词序、助动词、动词搭配和短语结构识别成分；多个规则产生互斥解析时返回歧义状态。
4. 中文解释由规则及模板生成，记录规则编号，便于核查和回归测试。
5. 纠错独立检查受支持的局部模式。错误句无法形成完整结构时，可以返回明确命中的纠错，但不能把局部结果当作完整分析。
6. 区分完整分析、部分分析、超出范围和存在歧义；提示尚未覆盖的检查范围。“未命中错误规则”不显示为“句子完全正确”。

词典、规则和解释模板随应用打包，运行时不从网络补全。规则执行应有长度和计算预算限制，避免异常输入卡住页面。

## 数据协议

在界面接入前确定 TypeScript 类型和运行时校验规则，并用固定样例验证：

- 结果包含原始输入、输入版本、规则版本、分析状态、句子用途、基本句型、复杂程度、成分节点和纠错项；无法判断的分类允许为空。
- 位置统一使用原始 JavaScript 字符串的 UTF-16 索引，采用左闭右开区间 `[start, end)`。不先清理空格或替换引号再计算位置。
- 成分使用本次结果内唯一的节点 ID、角色、父节点 ID 和一个或多个区间。支持短语内部嵌套和疑问句中不连续的动词成分，不使用单层互斥标签表示所有结构。
- 例如 `a useful book` 可以整体为宾语，`useful` 同时作为其内部定语。预留分句节点及归属关系，复杂句展示后续实现。
- 祈使句省略的主语可以记录为隐含节点，不伪造原文区间，也不自动判为缺失错误。
- 纠错项包含规则编号、原因、适用上下文、原文区间和替换文本。协议支持替换、删除和插入；插入使用 `[p, p)`，但协议能力不代表第一版支持所有纠错类型。
- 校验区间边界、原文匹配、节点引用与父子关系，禁止循环引用。允许合理嵌套；同一纠错项的多个编辑区间不得冲突。结构合法性和语法判断正确性分别验收。

## 交互与结果失效规则

- 启用分析按钮及明确显示的快捷键；提供处理中、失败、部分支持、超出范围和歧义状态，失败时保留输入。
- 每次编辑、选择例句或应用修改都更新输入版本，立即使旧标注与旧建议失效，禁用旧建议的应用操作。
- 分析结果只允许更新其对应的输入版本；若异步任务完成时输入已变化，丢弃过期结果。
- 应用建议前检查输入版本和待替换原文；一次只应用一条建议，随后重新分析。新结果返回前不能继续应用其他旧建议，避免字符位置变化或建议互相影响。
- 成分嵌套通过层级切换或详情展示；第一版不要求复杂句可视化，但不能把短语与其内部修饰成分混成同一平面。
- 将现有“支持陈述句、疑问句与复合句”改为与第一版覆盖范围一致的说明。原型阶段保留“示例分析”提示，功能完成后再声明真实分析能力。

## 隐私与本地运行约定

- 句子只在浏览器内处理，不发送到服务端、第三方接口、遥测或错误上报服务。
- 默认只保存在页面内存中，不写入浏览器持久存储或日志；刷新后不恢复上一次输入。
- 功能完成后，页面可说明“基于本地规则分析，句子无需上传”，同时明确有限的规则覆盖范围。
- 验收时检查网络请求和日志，并在断网条件下完成输入、分析、修改和重新分析流程。

## 第一版验收门槛

在扩展规则前固定预期答案，避免只用实现时的示例证明正确：

1. **基本分析**：五种基本句型每类至少 5 个词汇或结构有变化的正确句；四种句子用途每类至少 3 个正确句，可以与前述样例重叠。逐项核对分类、角色、位置、层级及中文解释。
2. **纠错**：三类规则每类至少 5 个错误句和 5 个无需修改的对照句。必须覆盖 `She go to school.`、`Does she go to school?` 和 `She can go to school.`，分别验证建议与不误报。
3. **范围边界**：至少 10 个未知词、歧义、并列句或复杂结构样例；不得强行返回完整且确定的解析。
4. **数据与交互**：覆盖重复单词、多空格、标点、非 BMP 字符的位置处理，以及插入、删除、嵌套区间和非法区间校验。覆盖空输入、长度边界、多句输入、连续点击、分析期间编辑、应用建议后旧结果失效和失败后重试。
5. **通过要求**：已承诺支持的固定样例全部满足预期；正确对照句不得产生错误修改建议；所有位置与状态校验通过。另用至少 20 个未参与规则编写、但属于约定范围的新句子复核，记录分析成功、误判和无法分析数量；范围内的新句子应正确分析，发现的问题修复后加入回归。小样例通过不代表任意英文的准确率。
6. **工程与体验**：提供可重复运行的规则测试命令，类型检查及构建通过；手机布局可用，键盘可完成核心流程，处理中及范围提示可访问；断网分析不依赖远程资源，网络请求和日志不包含输入句子。

## 交付依赖与交付物

第一版本地交付需要：

1. 确定可随应用分发的词典来源、许可及版本；若使用自建小词典，明确词汇覆盖范围。
2. 完成规则引擎、固定样例和自动回归测试，以及本地启动、构建和限制说明。
3. 在 README 中记录实际验证过的运行环境和命令。现有项目基于 React、TypeScript、Vinext / Vite；沿用本地开发结构，不为规则分析新增远程服务。

模型 API 和 GitHub 认证均不作为本地功能开发或验收的前置条件。源码同步到 [lintrin/grammar-analysis-web](https://github.com/lintrin/grammar-analysis-web) 及在线部署作为独立交付事项，在需要发布时确认认证和部署环境；本计划的修改不触发提交、推送或部署。
